# S1 · Terraform

The console-built S1 stack, described in hand-written HCL and **imported**
rather than recreated. `terraform plan` reports no changes, which is the proof
that the code matches what is actually running.

11 resources. Nothing in AWS was created, changed or destroyed to get here.

## Why import rather than destroy and rebuild

The obvious approach is to tear down the console-built stack and `apply` a fresh
one. That was rejected for three reasons:

- The site would be down for the rebuild.
- A new hosted zone gets four new name servers, so the four NS records at the
  registrar would need editing and DNS would need time to propagate. That is
  real downtime bought for no learning.
- A successful `apply` proves the code can build *something*. A clean `plan`
  against existing infrastructure proves the code describes *this* thing,
  attribute by attribute. The second is the stronger claim, and it is also what
  you actually do in a job that hands you infrastructure someone clicked
  together.

## Layout

| File | Holds |
|---|---|
| `providers.tf` | Two AWS providers: us-west-2 default, us-east-1 aliased `use1` |
| `variables.tf` | `account_id`, declared with no value |
| `route53.tf` | Hosted zone |
| `route53_record.tf` | Alias A at the apex |
| `acm.tf` | Certificate, us-east-1 |
| `acm_validation.tf` | The DNS validation CNAME |
| `s3.tf` | Bucket, public access block, encryption |
| `s3_policy.tf` | The OAC bucket policy |
| `cloudfront_oac.tf` | Origin access control |
| `cloudfront.tf` | Distribution, both cache behaviours |
| `waf.tf` | Web ACL, three AWS managed rule groups, 925 WCUs |

## Running it

Needs a `saa` profile in `~/.aws/credentials`, and a `terraform.tfvars`:

```
account_id = "000000000000"
```

```
terraform init
terraform plan
```

Expect `No changes. Your infrastructure matches the configuration.`

## What is deliberately not committed

| Path | Why |
|---|---|
| `terraform.tfvars` | Holds the account ID |
| `terraform.tfstate` | Holds the account ID, the full bucket policy and every resource attribute, in plain text |
| `.terraform/` | The provider binary, regenerated by `init` |

`.terraform.lock.hcl` **is** committed, so anyone running `init` gets the same
provider version and checksums.

State files are the ordinary way people leak account detail out of a public
repository without noticing. The `.gitignore` went in before the first resource
was written rather than after.

## Two providers for one account

CloudFront reads certificates only from us-east-1, and CloudFront-scope WAF web
ACLs only exist there. Everything else is us-west-2.

Terraform has no concept of a global service, so a fact that `DECISIONS.md`
states in prose becomes a second provider block plus an explicit
`provider = aws.use1` on exactly two resources. The tool makes the constraint
structural instead of something you have to remember.

## What the import caught

Import adopts a resource, but **every attribute left out of the HCL gets the
provider's default rather than the real value.** Two of those defaults were
wrong:

| Resource | Attribute | Provider default | Reality |
|---|---|---|---|
| `aws_route53_zone` | `comment` | `Managed by Terraform` | empty |
| `aws_cloudfront_distribution` | `tags` | none | `Name = cedar-clinic-site` |

Both would have been written to live infrastructure on the first apply. Neither
was visible without reading the plan line by line. That is the argument for
insisting on a clean plan rather than stopping at a successful import.

Reading the live CloudFront config also caught a wrong claim in `DECISIONS.md`
about compression. See the correction there.

One provider quirk worth knowing: `aws_wafv2_web_acl` rejects
`description = ""` with *expected length of description to be in the range
(1 - 256)*. An empty description has to be absent, not blank.

## Teardown

`terraform destroy` should tear down all 11 resources in dependency order,
which would replace most of `TEARDOWN.md`.

**Not tested.** Nothing has been destroyed or rebuilt here, so that is reasoning
from a clean plan rather than something observed. Proving it means destroying
the stack, applying it back, and accepting that the hosted zone returns with
four new name servers and a round of registrar edits and DNS propagation.

The four NS records at the registrar are manual either way, because they are not
in AWS.
